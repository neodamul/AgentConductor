# Native review after a plan starts

The Workspace Review step must distinguish a proposal awaiting human approval from a phase that already started. Returning from a completed run can leave the stored proposal phase as `starting`; showing its task cards as `Pending` suggests that approval or execution is still available and misrepresents the run.

The native Review pane now checks the persisted proposal phase. For `starting`, it shows a localized explanation directing the user to Agent Room for results or to edit the goal before preparing another phase. It omits stale task cards and the old proposal digest. Other proposal phases retain the existing review rendering.

Regression evidence: `tests/native_ui_probe/review_width.rs::an_already_started_plan_is_not_presented_as_pending_after_returning_to_workspace` renders a completed run with `proposal.phase = starting` and asserts the explanation appears while stale `task-0` is absent. One isolated native package window visibly showed the localized started-state explanation and omitted old task cards. An earlier custom-target package attempt was rejected after hash comparison exposed a stale default `target/release` binary; rebuilding with the repository release target fixed it. Windows behavior and exact-head GitHub CI remain open. This is not a new end-to-end workflow acceptance; the conservative packaged workflow count remains 1/25.
